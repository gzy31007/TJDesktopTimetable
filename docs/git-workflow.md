# Git 工作流

本文是项目协作约定：分支与版本线的分工、任务交付步骤、历史与发布边界。它不表示远端分支、Actions 或 GitHub 设置已经生效。三者要分开看：约定以本文为准，初始化行为以 [bootstrap.py](../scripts/git/bootstrap.py) 与其[最小 fixture](../scripts/git/test_bootstrap.py) 验证为准，平台保护以 GitHub 上的实际设置与读回为准。文档本身不构成强制。

本文只补版本线与交付流程，不替换现有的提交格式、核心测试、安全验收运行器、真机交互验收与用户数据保护要求。这些 Git 流程术语属于交付约定，不写进课表业务词汇表。

## 三条版本线

- `main` 保留已提交历史，是默认分支。不删除、不改写、不切换默认分支，日常任务不直接向它提交。
- `release/<major.minor>` 承载该版本的开发与验收。普通任务从经核实的固定基线建立任务分支，PR 回到同一条版本线。
- `stable` 承载发布晋级候选，使用独立整理过的历史，不接收逐个开发提交的常规合并。候选不等于已发布：stable 最新提交可能仍在构建或发布失败。发布是否成立，以正式 Release、不可变版本标签与实际受检 stable 提交的对应关系为准。晋级由维护者逐次批准，普通合并权限不包含推进 stable、决定版本或发版。这保留开发历史，也让经批准的整理提交成为未来自动发版的入口。

## 开工核对

动分支之前按顺序核对，任一项对不上先停下问维护者：

1. 工单正文、评论与验收条件，确认本次交付范围。
2. 目标版本与对应 `release/<major.minor>`。版本不明确时先确认，不自行挑一条线。
3. `origin` 指向 gzy31007/TJDesktopTimetable，本地 refs 与远端同名分支、标签状态符合预期。
4. 工作区 dirty 内容：哪些属于本任务，哪些是先前遗留。遗留内容原样保留，不计入本次交付。

基线取经核实的 release 提交 SHA。分支 tip 会移动，后续任务固定用核实过的 SHA。

## 任务分支与交付

- 按独立交付建分支，不按会话或代理数量拆。同一交付的阶段提交留在同一分支。
- 从核实过的 release SHA 建立任务分支。获准任务内可以做阶段 commit，也可以 push 任务分支；中途失败或暂停时如实交接，说明已推送的内容与未完成部分。
- 适用检查通过才创建 PR，PR 回到同一版本线。标题沿用 Conventional Commits，英文类型加中文简述。
- PR 正文用 `Refs` 或 `Related` 引用实施票，不用 `closes`、`fixes` 一类自动关票关键词，避免合并时提前关票。
- Standards 与 Spec 审查无阻断项、适用检查通过，才自动合并。普通任务用 merge commit，保留阶段提交与 PR 边界。
- 合入后逐项核对实施票的验收条件，满足才关票。失败、未完成或仍需人工验收时保持 open，不以编译通过替代真实交互验收。

## 历史与暂存

- 已 push 的历史默认只追加。不 amend、不 rebase、不强推已推送的提交。
- 显式暂存本任务文件，逐个给路径。不用 `git add -A` 或 `git add .` 把旧 dirty 一并带进提交。
- 不顺手 stash、restore、clean 或清理别人的改动，也不用改 `.gitignore` 把未提交内容藏起来。
- 以下操作另行取得批准：向上游仓库提 PR、操作第三方仓库、改写历史、每个新 worktree，以及完整源码或依赖副本。

## 首次初始化

执行前重新核实下面两个事实，任一变化先停下核对预期，不沿用本文记录：

- 当前已提交 main：`4d79f8c0cedc7c8e6058129e6468d6e3365bfc73`。
- 正式发布 `v1.6.1` 是 annotated tag，解引用到实际发布提交 `c296b411b708bfb9b234a7e5e8d7d00037705d1a`。

首次 `release/1.6` 从执行时重新核实的当前已提交 main 建立。这是迁移例外，用来保留已提交的开发成果；未来新版本线仍从上一正式发布的精确标签开始，不从旧版本线 tip 或 stable 整理历史起步。

首次 `stable` 从 `v1.6.1` 对应的实际提交建立。取 annotated tag 解引用后的提交，不用标签对象本身的 SHA。

已有同名本地或远端 refs 时，先核对是否同一预期来源。不覆盖、不强推。重复初始化保持幂等：目标已存在就跳过并报告，不改写已有分支。

初始化本身不发布。不回补旧版本，不晋级 1.6.2，不创建真实 Release。#40 的范围也不包含公开真实版本。

### 初始化操作与复核

先核实正式 Release 并审读两个源提交中的全部 Actions，不以工作区未提交的工作流为准。此次两个来源各有一个只构建的 CI，以及两个仅由 `v*` 标签或手动 dispatch 触发的发布工作流，没有分支发布触发器。初始化只推送两个指定分支，不推标签、不调用 dispatch 或发布 API。未来工作流有变更就重新审读，不能照抄旧审计值。

在仓库根运行下面命令，默认只输出计划。它校验 origin 的 fetch 与 push URL、本地和远端 main、解引用后的 v1.6.1、人工审计的工作流树以及同名分支。这里的工作流树 SHA 是人工审读的身份绑定，不是自动判定工作流安全的扫描器。

```sh
python3 scripts/git/bootstrap.py \
  --main-sha 4d79f8c0cedc7c8e6058129e6468d6e3365bfc73 \
  --published-sha c296b411b708bfb9b234a7e5e8d7d00037705d1a \
  --main-workflows-tree e9465ec599fe3bfa518afce7c56cce0c51e5b974 \
  --published-workflows-tree 22b51d2b3ebaa4f009828a1105b936165c206409
```

核对计划后追加 `--apply --push`，创建本地与远端分支。远端使用原子推送和空 lease，只允许创建缺失分支，不能覆盖已存在分支；中途失败保留已完成部分，按输出读回再决定，不自动回滚。重复执行会校验并跳过同来源分支。该工具只用于首次迁移，release 线交付新提交后不再是可重复初始化状态。

完成后读回本地和远端分支、全部标签、正式 Release 与 Actions，确认源与目标精确对应、标签和 Release 未变、没有发布工作流因初始化启动。脚本不代替 GitHub 状态核对。合成测试用 `python3 -m unittest discover -s scripts/git -p 'test_*.py' -v`，只使用临时合成仓库，不访问 GitHub。

## release 到 stable 的候选晋级

首次初始化、日常 PR 合并与发布复制是三个不同操作。候选晋级使用 [逐候选批准与操作说明](stable-promotion.md)：固定已验收源 SHA，以完整 tree 创建 stable 的单父追加提交，保留来源、版本与验收记录；默认只读计划。#41 交付脚本与合成验证，不推进真实 stable，也未接通生产 Actions；触发契约及并发失败边界见该说明。

## 发布边界

- 版本号与发布说明在 release 线准备，流水线不自动递增版本。
- 维护者批准晋级 stable 后，由统一流水线执行同提交测试、构建、草稿与资产核验，通过后公开。真实发布验证 stable 的确切提交。此处是后续生产入口的目标，不声称当前已启用。
- 新生效的生产自动发布入口属于 #42 至 #44 的范围。本次不把现有未提交的发布门禁候选整体纳入，也不把它们的改动当作本任务的交付内容。
- 普通任务的自动合并权限到此为止，不包含晋级 stable、决定版本或发布。
- 默认分支切换、分支保护与环境审批设置不在本文范围。需要时另行核对 GitHub 上的实际配置。
